01 · The problem

The app is opened with intent. Not with habit.

Users know Testbook is where the mocks are. They don’t know what the smallest useful action is today — and their progress is buried three taps deep.

Today
Home→Tests→Test series→Exam modal→Section list→Pre-instructions→Start
6 transitions before the first question
With the widget
Home screen→Tap widget→Pre-instructions→Start
2 transitions to the first question
94

screens, zero OS surfaces

Twelve product lanes, a complete event catalogue — and no widget, shortcut, or launcher presence in the spec.

80%

of the data already exists

getTestSubmissionsStreak() already returns the weekly timeline, badges, and the next test. The daily streak is the missing piece.

0

daily streak for all users

The only live daily streak is Super-only. The old StudentStreaks model is unused. We build a real one — or we don’t show “Day 6”.

“A widget is not another dashboard. It is a daily commitment contract.”

Anatomy

Five decisions, in order of importance.

  1. 01
    Weekly hero

    3/5 tests this week — the exam-specific goal. Same number as the Tests tab, so the widget never contradicts the app.

  2. 02
    Daily subline

    🔥 Day 6 — the habit loop. Server-driven; hides gracefully if the daily-streak service is unavailable.

  3. 03
    Day pills

    Seven study-day states: done, today, upcoming, missed. Momentum without a chart.

  4. 04
    AI micro-coach

    One diagnostic line, max 64 characters. Specific beats cheerful: “Algebra 42% — 10 Qs.”

  5. 05
    Full-width action bar

    The AI line, a short action label, and a blue arrow. It reads as a button, not a chip. Never two competing CTAs.

Prompt rules
  • Live preview, not a static illustration.
  • Two actions only: Add widget / Not now.
  • “Not now” suppresses for 14 days, max 3 lifetime.
  • requestPinAppWidget() on Android 8+; illustrated fallback when unsupported.
  • Never on cold launch. Never twice in one session.
05 · Sound + haptics

The widget is silent. The Brief is the tap on the shoulder.

Android widgets cannot play audio or vibrate on update. We put sound and haptics where they belong: an opt-in notification, plus an Android 16 Live Update for the evening window.

  • No audio from the widget.
  • No vibration on widget data updates.

  • No Pass audio on every notification.

Refresh rules
  • updatePeriodMillis = 0; do not rely on the 30-minute system minimum.
  • Refresh on app open if data is > 15 min stale.
  • Show “Updated 3h ago” after 6 hours; never a blank widget.
  • Per-block fallbacks: one API failure must not blank the card.
  • Refresh on timezone, locale, exam-date, and pass changes.

07 · Measurement

Measure installs and taps. Never claim impressions.

The launcher does not report when a widget is visible. “Active” is a proxy: last successful update or tap. “Incrementality” requires a randomised prompt holdout.

Illustrative targets, not actuals. Calibrate after the 5% experiment.

D7 retention lift+1.5–2.5 pp
Notification opt-out≤ 2%
What is measurable

Installs via onEnabled/onDeleted, active via heartbeat, data freshness via data_age_sec, taps via deep-link UTM.

What is not

Widget impressions. The launcher never tells you when the card is on screen. Do not put “views” in the dashboard.

The bias trap

Widget installers are already engaged. Randomise the prompt, not the widget, or retention lift is fiction.

08 · Roadmap

Eight weeks to a habit surface.

Shortcuts first, widget second, intelligence third, scale last. If the daily-streak service slips, ship the weekly hero and enable the subline server-side later.

Week 1

Spike

  • Glance + pin API
  • FCM refresh
  • OEM matrix
  • Snapshot contract
Weeks 2–3

Intelligence
